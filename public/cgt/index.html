How to log a real card (until a backend is wired in)

Edit public/cgt/data/cards.json by hand and add an object to the cards array. Leave any field you do not have a real answer for as null, do not fill it in with a guess. If the real data already exists as a CSV export from the tracker file, the Import CSV page will map its columns to this schema, validate it, and hand back a ready-to-save cards.json instead of retyping everything by hand.

Run node public/cgt/data/validate.js after every edit. It catches duplicate ids, a missing or unlabeled valuationBasis on a priced card, a comp-estimate with no compNote explaining what it is based on, and bad dates. It also warns (not an error, since owning two real copies of the same card and grade is a real thing) when the same card name, year, grading company, and grade shows up on more than one row, in case a row got copy-pasted and only the id was changed. It runs the same warning (again, not an error, since a real low-pop anomaly can genuinely outsell a common higher grade) when a higher numeric grade of the same card is priced below a lower grade of it, in case a price or grade got typed against the wrong row; this one also shows up on the dashboard itself under "Possible grade/price mix-ups" when it finds anything.

A priced card gets a stale badge once its datePriced is more than 180 days old. That is not an error, card market prices just drift over months, and it is a nudge to re-check the price next time you are in this hub, not something to fix immediately.

When you re-check a price on a card that already has one on record, don't just overwrite estimatedValue. First push the card's current estimatedValue, datePriced, and valuationBasis into a new entry at the end of its priceHistory array, then set the new researched numbers as the current fields. This is the same "never silently lose a real number" rule as everything else here, applied to re-pricing: it's what lets the card's detail view show how its price has actually moved instead of only ever showing the latest number with no memory of what it changed from. A card that has only ever been priced once has no history yet, that's normal, leave priceHistory off entirely or as an empty array.

If gradingCompany is PSA, BGS, SGC, CGC, or KSA, the card's detail view links out to that company's real cert-verification tool (PSA and BGS link straight to the cert when certNumber is filled in, the others open the lookup tool for you to enter it by hand since they don't expose a direct-link URL). HGA has no public lookup tool as of this writing, so no link is shown for it.

How to log a grading submission (cards sent off, not back yet)

A submission is a batch of cards currently at a grading company, before it has grades back. It is tracked separately from cards.json because it has no grade, cert number, or price of its own yet. Edit public/cgt/data/submissions.json by hand and add an object to the submissions array. Once a batch actually comes back, add the real graded cards to cards.json with their real cert numbers, and set this submission's status to "returned" with a real returnedDate rather than deleting the row, so there is still a record of how long that batch actually took.

Run node public/cgt/data/validate.js after every edit. It validates submissions.json the same way it validates cards.json: duplicate ids, a status outside the known list, a returnedDate that disagrees with status, and bad dates.

How to log a "should I grade this?" candidate

A candidate is a raw (ungraded) card being weighed against the real cost of grading it, before anything is shipped. It is tracked separately from both cards.json (already graded) and submissions.json (already shipped) since it has neither a grade nor a tracking number of its own yet. Edit public/cgt/data/candidates.json by hand and add an object to the candidates array. Leave any field with no real answer as null, same rule as everywhere else. Once a candidate is actually shipped, add a real row to submissions.json and set this row's decision to "submit" rather than deleting it, so there is still a record of the reasoning behind sending it.

Run node public/cgt/data/validate.js after every edit. It validates candidates.json the same way it validates cards.json: duplicate ids, a missing or unlabeled basis on either priced field, a comp-estimate with no note explaining what it is based on, and bad dates.

The verdict shown on the dashboard (Worth grading / Marginal / Not worth it / Needs more data) applies the common "2x margin" rule of thumb from real card-grading ROI writeups: expected gain (estimated graded value minus raw value minus grading and shipping costs) should clear the total cost by at least 2x before it counts as clearly worth it, since the card could come back at a lower grade than expected. A margin above 0 but under 2x shows as "Marginal" rather than "Worth grading", and any candidate missing one of the three real numbers the math needs (rawValue, expectedGradedValue, estimatedGradingCost) shows "Needs more data" rather than a guessed verdict.
