How to log a real prospect (until a backend is wired in)

Fastest path: click + Log new prospect above, fill in whatever fields you actually have real answers for, and it generates a paste-ready JSON object with the id, dates, and nested objects already shaped correctly, plus the same backfill warnings validate.js would raise. Paste the result into the prospects array below. If you just finished a research pass and have several candidates at once, use that same modal’s Quick add tab instead: name, company, category, and hook only, one row per candidate, all logged at the researched stage in one paste.

Or edit public/csm/data/prospects.json by hand and add an object to the prospects array. Leave any field you do not have a real answer for as null or [], do not fill it in with a guess.

To correct a field on a prospect who is already logged, open that prospect’s card and use Edit this prospect’s details inside its detail view instead of hand-editing the JSON directly, it is pre-filled with the current values and raises the same warnings. Stage moves, content ideas, and outreach touches each have their own small generator further down that same detail view.

Run node public/csm/data/validate.js after every edit. A typo in stage does not throw an error, it just makes the prospect silently vanish from the board. The validator catches that, plus duplicate ids, bad dates, an invalid contactChannel.type, and social numbers logged without an asOfDate.

Before a risky hand-edit, click Download backup (.json) in the header first. Unlike Export CSV, which flattens each prospect to one row and drops stageHistory, the backup file keeps the full prospects.json and stages.json structure exactly as loaded, so a bad edit can be diffed against or restored from a known-good copy. This is a local download only, nothing is uploaded anywhere.

idUnique slug, e.g. "company-person-name"
stageOne of: researched, outreach-sent, silent-replied, in-exploration, client (see data/stages.json)
stageEnteredDateISO date this prospect moved into its current stage. Update it every time stage changes. Once logged, the board flags the card as stalled if it sits past that stage's stall threshold in data/stages.json.
contactChannel.type"named-decision-maker" or "generic-inbox", this is the field with the biggest real effect on reply rate, always fill it in as soon as it is known
socialSnapshot.asOfDateThe date the follower/engagement numbers were actually pulled, never today's date by default. Past 90 days old, the board flags it as due for a refresh instead of silently showing an aging number as current.
nextActionPlain text describing what actually needs to happen at the next touchpoint (e.g. "Follow up referencing their latest Douyin post"), not just a date. A due date with no concrete next step is one of the most common ways real pipeline deals quietly stall.
nudgeScheduledoNotNudgeBefore and nudgePoint, both ISO dates (YYYY-MM-DD)
outreachLogArray of { "date": "YYYY-MM-DD", "type": "initial-send"|"nudge", "note": "..." } (note optional). The real touch-by-touch record: since most replies come from a follow-up, not the first message, this is how many times someone was actually contacted, separate from the single sendDate/nextNudgeDate fields, which only hold what already happened once or what's scheduled next. Log one initial-send entry, then one nudge entry per real follow-up. Shown oldest first.
contentIdeasArray of { "date": "YYYY-MM-DD", "idea": "..." }. This is a dated log, not a wishlist: date is when the idea was actually logged, not when you might use it. Shown newest first.
stageHistoryArray of { "date": "YYYY-MM-DD", "stage": "outreach-sent" }, oldest first, logged each time the prospect actually moves to a new stage. This is how real time-in-stage and pipeline velocity get tracked instead of only knowing the current stage. The last entry's stage should match the prospect's current stage, the validator warns if they drift apart. Leave it as [] until you start logging moves going forward, do not backfill guessed dates for past moves.

Stalled in stage

May need a new approach

Still sitting in Outreach Sent after 3 or more real touches logged in outreachLog (the initial send plus every real nudge, not just a scheduled date). A common signal in cold outreach: past that many identical touches with no reply, the issue is usually the hook or the channel, not that one more nudge is due. Worth trying a different angle, a different channel, or the named decision-maker instead of the generic inbox, rather than sending a near-identical follow-up again.

Possible duplicates

Same name and company logged on more than one entry. Could be a real second contact at the same company, or a copy-pasted row from the "Log new prospect" generator that only got a new id. That generator only guards against an exact id collision, not a near-duplicate person, same check validate.js runs.
