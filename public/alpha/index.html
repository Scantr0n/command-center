How the live connection works

This page fetches /api/alpha/live. That route, in server.js, tries Alpha's real daemon first (GET-only, the fixed whitelist above) and falls back to the honest static placeholder in public/alpha/data/status.json if the daemon isn't reachable, for example on a machine other than Jack's Mac, or if the daemon isn't running. There is no write path in either direction.

Run node public/alpha/data/validate.js after editing the static fallback file. It rejects a live value set without live.asOf, and rejects any key that looks like real P&L, balance, win rate, or trade-count data, since that file has no legitimate way to know one.

This browser tab also remembers the last real, connected reading of the slow-changing fields (kill switch, regime, drawdown, debate panel, genealogy, anomaly count) in its own localStorage, purely client-side. If the daemon drops momentarily, those sections keep showing that last real reading with an explicit "last known, aged" label instead of blanking to "awaiting connection". Account and positions never do this: they revert to "awaiting connection" immediately, since a frozen dollar figure is misleading in a way an old kill-switch reading is not.

The "Market open / closed" pill next to the headline status is computed entirely in this browser from the current time and a fixed 2026 NYSE regular-session calendar (9:30am to 4:00pm ET on trading days, 9:30am to 1:00pm ET on the two annual early-close days, closed on the 10 published NYSE holidays); it does not come from Alpha at all and never will, since Alpha does not expose a market-calendar endpoint and doesn't need to. It exists purely as glance context for reading everything else on this page, for example an empty Positions table on a Saturday means something different from the same empty table at 10am on a Tuesday.

The "Fetch" reading next to the Connection strip is a real, measured round trip: how long this browser's own request to /api/alpha/live just took to resolve, timed around that request in app.js. It reports this page's own speed talking to Command Center, not Alpha's daemon's own internal latency, since Command Center may itself be answering from the static fallback file rather than a live round trip to Jack's Mac. Recorded per browser only, in localStorage, same as the connectivity and regime histories above; the averaged figure next to it covers the most recent 20 samples.

The small trend line next to the Current drawdown and Robustness score meters under Position sizing is the same idea applied to those two readings: Alpha's live feed sends only the current value, never a history, so this browser keeps its own honest, capped log of real readings it has actually polled and draws it as a sparkline, same "recorded by this browser only" caveat as the connectivity, regime, and fetch-latency histories above. Max drawdown has no sparkline since it is a running peak-to-trough maximum and can only stay flat or rise within an episode, never the up-and-down a trend line is useful for.

The "Time in each regime" bar above the regime change list aggregates the same real per-transition durations that list already shows into a single total per regime label, real regime-analytics dashboard convention (pairing the current label with how conditions have actually evolved, not just the latest reading). Built only from this browser's own recorded transitions, same "since it started observing" caveat as the chronological list beside it, never backfilled with a guess at what happened before this tab was open. Only appears once at least two distinct regimes have actually been observed; a single regime for the whole window would just restate the "Detected regime" tile above under a different label.

"Enable critical alerts" turns on a native OS notification, using the browser's own Notification API, the moment this tab's headline first shows the kill switch engaged or a page error, if this tab is not the one currently focused. Nothing is sent anywhere for this: the browser shows the notification locally from whatever this tab already has on screen, the same read-only data described above. The choice to enable it is remembered per browser in localStorage; permission itself is controlled entirely by the browser, and can be revoked at any time from its own site settings.

system.*Static architectural facts (agent count, feature list). Real, does not change with market conditions, safe to hand-edit only when the architecture itself changes.
system.lastVerifiedAtISO datetime this architectural description was last actually confirmed to match Alpha's real code, or null. Unlike everything under live, these facts have no daemon to report their own freshness, so this is a hand-set trust signal instead: update it whenever the feature list or agent count is re-checked against reality, not on every unrelated edit to this file. Past 90 days old, the Architecture section heading flags it "due for a recheck" in amber, the same stale-but-not-wrong treatment this page already gives a live reading a few minutes old, just on a timescale that fits a fact that only changes when the code itself does.
connection.connectedtrue once a real feed exists and is currently reachable, otherwise false.
connection.checkedAtISO datetime of the last time connectivity was actually checked, or null.
connection.history[]Append-only log of past connectivity checks, oldest first, each a real result of an actual check, never backfilled or estimated. Each entry needs at (ISO datetime) and connected (true/false, never null, since a check that never resolved is not a result), plus paused (the daemon's real kill-switch reading at that same check, true/false, or null whenever connected is false, since an unreachable daemon has no real kill-switch reading to attach). Drives the strip of ticks under the connection status, the daily uptime bars beneath that (one bar per real calendar day, colored by that day's real up/down ratio), and the recent-incidents list beneath those (each incident there is just a run of consecutive "not connected" entries from this same array, grouped into a start time, end time, and duration; nothing estimated). The live route in server.js now persists this itself: every request to /api/alpha/live already performs a real health check against Alpha's daemon, so that route logs its own real result (capped to the most recent 500) to public/alpha/data/connection-history.json, a local, gitignored file next to status.json, and returns it here, shared across every browser hitting that same running server. A browser still keeps its own localStorage copy as a fallback for the brief window before that file has any entries, or if this page is ever served with no server behind /api/alpha/live at all, labeled "recorded by this browser only" whenever that fallback is the one actually showing.
live.asOfRequired whenever any field below it is set. ISO datetime the live reading was actually taken at.
live.regimeCurrent detected market regime label, or null. The server sends only this single current value, never a history; the "Regime history" section below builds its own log of real transitions this browser has actually observed (a new value that differs from the last one it saw), timestamped and kept in this browser's own localStorage, labeled "recorded by this browser only" for the same reason as the connectivity-check history above. Nothing estimated or backfilled, only real observed changes.
live.killSwitch.engagedtrue / false / null if unknown.
live.killSwitch.lastTriggeredAtISO datetime of the most recent real false-to-true flip in connection.history[].paused, or null until this server has actually observed one. Derived server-side in server.js from that same shared history, same "since this server started observing" honesty as everything else built from it: it never claims "never triggered" just because a transition predates this history existing, and never guesses at a transition that happened while the daemon was unreachable (a gap where paused is null on either side breaks the comparison rather than assuming one).
live.positionSizing.activeModeWhich sizing rule is currently driving position size (e.g. "drawdown-based"), or null. The server sends only this single current value, never a history, same gap live.regime has; the "Sizing mode history" list under Position sizing builds its own log of real transitions this browser has actually observed (a value that differs from the last one it saw), timestamped and kept in this browser's own localStorage, labeled "recorded by this browser only" for the same reason as the regime and connectivity histories above. Nothing estimated or backfilled, only real observed changes.
live.positionSizing.currentDrawdownPctCurrent drawdown as a number from 0 to 100, or null. Drives the drawdown meter, never a dollar figure.
live.positionSizing.maxDrawdownPctDeepest peak-to-trough drawdown observed, 0 to 100, or null. Always >= currentDrawdownPct when both are set, since it can only be as small as the current reading. Shown as its own meter so a shallow current reading is never mistaken for a shallow episode.
live.positionSizing.robustnessScoreCurrent reading from Alpha's robustness-based sizing, 0 to 100, or null. Robustness-based sizing is a named architecture feature in its own right (see Architecture below), distinct from drawdown-based sizing, so it gets its own meter here rather than being folded into the drawdown fields above.
live.debatePanelUnlike every other object under live, this one is never null or missing: the debate panel is a named architecture feature that is real but not yet active (pending an API key), so its state is always known, just not yet "on". active is required, true/false. blockedOn is a short string naming what it's waiting on (currently "API key"), or null once active is true. Unlike regime and sizing mode, the server sends no history for this one to build a transition log from either, but this one only ever flips once (pending to active, never back), so the Summary tile instead keeps a single "first observed active" timestamp in this browser's own localStorage the first time it actually sees active: true, labeled "first seen active" rather than "activated at" since the real switch may have happened earlier if this tab wasn't open yet. Same "recorded by this browser only" honesty as the connectivity, regime, sizing-mode, and fetch-latency histories above.
live.anomalies.*stuckCount is how many agents Alpha's real /anomalies endpoint reported stuck as of the last check, or null whenever that one subrequest failed even while the rest of the feed answered (a real 0 and an unknown reading are never conflated: 0 means the check ran and found nothing, null means the check itself did not complete). checkedAt is the ISO datetime of that same check, required whenever stuckCount is set. Feeds the "Active anomalies" tile in Summary and the same last-known caching as kill switch, regime, drawdown, debate panel, and genealogy above; each stuck-agent detail is still also folded into the Activity log below as its own event, unchanged. A real positive stuckCount also moves the page's own top headline (next to the ALPHA title) off "Connected" to an amber "N stuck agent(s) detected" reading, the same match-the-highest-impact-signal rule status pages apply to their own top-line badge, so a stuck agent is visible without scrolling down to Summary; a null reading never does this, same honest-unknown rule as everywhere else.
live.genealogy.*Current generation, count of active lineages, and last breeding event, or null until known. live.genealogy.lineages[] is the wall itself, one card per lineage (id required, plus optional label, generation, agentCount, status of "active" or "retired", and a last-event stamp). Starts empty, honestly, same as every other array on this page; the aggregate counts above still show on their own once a feed knows only the totals, not yet the per-lineage detail.
live.accountEquity, cash, buying power, and day change, or null. Only ever populated by the live daemon proxy in server.js, never hand-edited into the static fallback (its own validator forbids balance/equity-like keys there on purpose).
live.account.equityCurveReal equity readings, oldest first, plain numbers with no timestamps. Forwarded straight from Alpha's own /equity-history endpoint, the same real feed server.js already used to compute the drawdown percentages above; only the already-trusted .v field is read from each point, capped to the most recent 200. Same live-proxy-only rule as the rest of live.account. Drives the equity curve chart under Account; hidden entirely with fewer than 2 points, same honest-empty-state rule as everything else on this page. No time axis: this page has never verified a timestamp field on these points, so the chart shows reading order, not elapsed time.
live.positions[]Real open positions (symbol, side, qty, entry/current price, market value, unrealized P&L), or an empty array. Same rule as live.account: live-proxy only. The table's "% of equity" column isn't its own field: it's computed client-side from each row's real marketValue against live.account.equity, the same derived-not-fetched pattern the Account section's own "Invested" tile already uses, and is left blank rather than a misleading 0% whenever equity isn't a real positive number yet. A single position at or above 10% of equity, a standard concentration-risk threshold, is highlighted the same amber this page already uses for "stale" and "pending" elsewhere.
events[]Append-only activity log: kill-switch triggers, regime changes, connection state changes. Each entry needs at (ISO datetime), type, and label; detail and tone ("neutral", "good", or "alert") are optional. Connection-lost/restored and kill-switch-engaged/released entries are both real and server-generated the same way: server.js derives them directly from real consecutive flips in connection.history[].connected and connection.history[].paused, so they show up even without a live daemon feed the moment this server's own connectivity or kill-switch reading actually changes. Evolution and anomaly events still need the real daemon feed to exist at all, so this sandbox has none of those to show yet.
changelog.jsonGenerated, never hand-edit. Run node public/alpha/data/changelog.js after committing changes to status.json, it reads this repo's real git history and regenerates the whole file from actual commit hashes, authors, and dates. Same pattern already proven at public/sondrik/data/changelog.js and public/csm/data/changelog.js, and drives the Data changelog section near the bottom of this page.
This browser's status

This page leans on a few browser features to work fully: localStorage for the connectivity, regime-history, and last-known-state caches described above, the Notification API for critical alerts, and a service worker for offline app-shell caching. Any one of these can be silently blocked (private browsing, a locked-down profile, revoked permissions) without the rest of the page failing, which just as silently mutes the feature that depended on it. This table is a real, live check of this browser, right now, on this device, so that silence is never mistaken for "nothing to report".
